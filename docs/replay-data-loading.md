# 回放数据加载

游戏决定何时请求和预取，网站的 `scripts/easyrpg-game-services.js` 负责缓存及相同请求合并。Player 保持通用的请求转交能力，不加入本作的分页或收藏规则。

## 浏览与缓存

- 接口的 `page` 仍以每页五条计算。可选 `pageCount=3` 一次获取十五条；省略时保持旧客户端的一页响应。列表同时携带开场元数据，进入详情不再单独查询。
- 网站适配层按自己、全员、收藏保存缓存，每类最多两批六页，优先保留当前批次和翻页方向上的相邻批次。游戏在当前页显示后立即沿翻页方向预取相邻批次，不等待按键空闲；详情停留 400 毫秒后预取当前录像。
- 首批返回 `snapshot`，后续批次沿用该索引序号上限，避免新对局插入引起重复翻页。正在浏览时保留当前缓存；从标题重新进入时先请求 `available` 核对账号，清除超过 60 秒的列表与详情缓存，并将光标重置到第一页。
- 录像按对局与 `revision` 复用，最多缓存两场，输入数组与开场变量预算合计 8 MiB。预取、播放和导出共用进行中的请求和已下载数据。预取使用低网络优先级，不触发重演、检查点生成或视频编码。
- 收藏成功后同步已缓存星标，并使收藏分页缓存失效。账号变化或未登录时清除个人缓存。个人观看方向和收藏状态只存在授权响应及客户端缓存中，不写入公共录像文件。
- 后台预取不锁按键，不显示失败提示；前台主动读取仍沿用现有错误行为。

## 录像索引与成品

`0063_netplay_replay_catalog.sql` 新增可播放候选索引，迁移按原有规则收录已完整上传的双端录像。分块写入时在同一条语句中检查双方结束标记，尚未结束的普通上传不追加索引查询。双方结束标记齐全后，只核对这一场的双端连续分块、开场及终局一致性；通过后建立索引，并通过 `waitUntil` 运行现有逐帧校验与整理流程。乱序分块补齐及被忽略的重试也可触发重新核对。

列表不再扫描全部原始分块。正常列表的一批十五条使用一次业务查询，详情复用其开场元数据。缺失开场索引的历史记录首次读取时仍从原始记录补齐，以后复用索引。

整理后的数据保存到 R2 的 `netplay-replays/v1/<对局>/<revision>.json`，只包含版本、开场状态与输入帧。每次请求仍验证登录、作品可读性和联机空间权限，再附加当前账号对应的摘要。成品命中不再查询分块或重新合并双方输入；旧录像或后台未完成的录像在首次播放时整理并保存。整理失败不缓存错误结果，后续主动读取可重试。

新增分块会使该场索引失效，上传入口重新检查后建立新版本。历史开场恢复记录的变更也会更换版本；标记为不兼容的录像继续隐藏。不同版本使用不同对象键，旧的后台任务不能覆盖新版本。原始双端记录保留。

## 发布与检查边界

发布候选需要应用新增迁移、按既有流程导入包含新版 `game-services.js` 的 Web runtime，再重打中日版游戏。无需修改 Player 源码或 APK 原生接口。固定开发种子同步迁移链，线上数据不会在本地开发时被写入。

本次使用临时内存 SQLite、模拟 R2 与服务桥检查分页、请求合并、收藏失效、账号隔离、旧录像恢复变量及乱序上传。请求计数不包含真实登录认证查询，也不代表浏览器、Android 实机或远端耗时验收。
