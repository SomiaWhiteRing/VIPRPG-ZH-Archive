# 产品方向与精简重构计划

状态：当前开发基线

认证、角色、授权和审计边界只以[认证与权限管理系统统一基线](./authentication-authorization-baseline-plan.md)为准；本文只定义产品信息架构。

本项目的公共产品是 RPG Maker 作品的游玩空间，不是博物馆、祭典宣传页或数据库展示页。
玩家应能快速发现作品、进入详情、在线游玩或下载，并在作品上下文中讨论。上传者应能在一次浏览器会话内，以尽可能少的步骤提交一个作品归档并看到处理结果。

## 1. 产品边界

### 玩家空间

- 首页负责推荐和发现，不负责解释内部归档模型。
- 根路径只维护一种作品发现首页，以登录态内容首页为交互和信息架构基准；不另做 HERO 式未登录介绍页。
- 作品是公共导航和页面层级的第一主角。
- 作品详情的第一屏只解决：这是什么、能否游玩、如何下载。
- 评论和反馈应绑定作品或版本，而不是依赖孤立的站内信流程。
- 作者、角色、标签、目录是搜索和筛选工具，默认不与作品并列抢首页注意力。

### 上传空间

- 上传是一次会话内完成的操作，不设计为长期项目管理。
- 流程保持：选择文件 -> 识别/关联作品 -> 填最少必要信息 -> 上传 -> 查看结果。
- 文件白名单、哈希、去重、preflight、commit、引用关系和服务端任务记录属于内部实现，不能为了简化 UI 而删除。
- 不把跨浏览器重启恢复、跨标签页接管、复杂本地任务历史或多设备接力当作产品能力；上传状态只保留当前标签页会话。

### 管理空间

- 管理空间承载内容、角色管理、归档一致性、存储和审计；谁能执行这些操作由统一认证授权基线决定。
- 管理页面可以暴露内部字段和危险操作，但不应反向决定公共首页结构。

## 2. 明确不做

- 不为未登录用户制作平台介绍 HERO、品牌宣传页或另一套首页结构；登录、注册和账户动作放在同一游玩空间的次级位置。
- 不在普通用户页面解释 Work、ArchiveVersion、manifest 或 R2/D1 存储关系。
- 不为了“推荐系统”提前建立用户画像、协同过滤或复杂事件流水线。
- 不把作者、角色、标签、目录做成首页的平级功能墙。
- 不把一次性上传包装成跨会话的长期任务中心。
- 不在没有真实数据和需求前新增评论、收藏、历史记录或推荐算法的完整模型。

## 3. 当前信息架构

```text
公共空间
  首页：推荐、最近加入、热门游玩/下载、讨论活跃、随机发现
  作品：搜索、筛选、分类浏览
  作品详情：简介、截图、在线游玩、下载、讨论
  辅助索引：作者、标签、角色、目录

账户空间
  我的账户、消息、收藏/历史（仅在功能真正存在后加入）

上传空间
  新建上传、当前会话进度、完成结果

管理空间
  内容、版本、用户、审计、维护
```

“最近更新”只表示真实的新版本或新归档；对于不会持续变动的作品，优先使用“最近加入”“热门下载”“讨论活跃”等真实内容分区。

## 4. 精简原则

1. 一个事实只有一个生产来源；UI 组件、标签映射和产品文档不各自维护同一套规则。
2. 先删除失效的 brief、历史执行计划和过期截图，再开始页面重做。
3. 先改公共玩家路径，不同时重写后台、上传、在线游玩和数据模型。
4. 只有有生产消费者、有外部契约或有数据安全作用的复杂度才保留。
5. 任何行为变化先写清影响范围和验证路径；纯文档删除不需要迁移层。

## 5. 实施阶段

### Phase 0：清理基线

- 本文档作为唯一的当前产品方向入口。
- 历史方案、已完成的临时计划和实验产物不作为项目指令或后续实现依据。

验收：`rg` 不再能从项目指令或工作流找到旧 festival brief 引用；架构文档链接仍然完整。

### Phase 1：公共首页和导航

- 首页改为作品推荐和发现流。
- 以原先登录态首页为基准：顶部导航、推荐/最近加入/热门游玩/讨论活跃等内容分区、账户和消息入口；未登录只减少账户动作，不切换为 HERO 宣传页。
- 公共主导航优先放作品；作者、角色、标签、目录移到筛选或更多入口。
- 不新增推荐算法，先使用可解释的数据库查询。

验收：根路径始终进入作品发现首页；未登录和登录态都能在两步内到达作品详情；详情可达在线游玩/下载；移动端无横向溢出。

### Phase 2：作品列表和详情

- 卡片展示真实封面/截图、简介、类型和可用动作；缺图时使用明确的文字占位，不生成抽象装饰图。
- 详情第一屏突出在线游玩和下载。
- 版本、归档和技术信息折叠或降级到次级区域。
- 讨论区域预留在作品上下文中；若实现评论，单独设计最小数据模型和权限。

验收：浏览 -> 详情 -> 游玩/下载完整可用；版本操作不丢；长标题和归档 ID 可换行。

### Phase 3：上传流程减法

- 把上传表单分成“必要信息”和“高级信息”。
- 保留浏览器 Worker、白名单、哈希、去重、preflight、commit 和当前会话进度。
- 全局 upload dock 只显示当前标签页会话内的内存任务。
- 在没有证据证明需要前，不新增 OPFS 全量缓存、多设备接力或长期任务中心。

验收：选择文件 -> 关联作品 -> 提交 -> 看到结果的路径清晰；失败、取消和权限状态可理解；归档完整性检查不回归。

### Phase 4：账户、讨论和上传者反馈

- 账户首页围绕消息、收藏/历史和上传者状态组织，仅展示已经存在的能力。
- 作品讨论、上传者回复和版本反馈作为独立功能设计，不把评论硬塞进现有 inbox 或归档表。

验收：评论权限、通知和上传者反馈边界明确；没有实现的功能不以“推荐/社区”文案伪装存在。

### Phase 5：后台和内部信息收束

- 公共体验稳定后再调整管理导航、归档详情、GC、审计和存储观测。
- 内部字段可以保留在管理页面，不回流到公共作品首屏。

验收：管理端仍可完成内容编辑、角色管理、归档维护和审计；危险操作有明确确认和回滚边界，访问控制符合统一认证授权基线。

## 6. 每阶段的最小验证

- `npm run check`
- 受影响页面在桌面和移动视口检查：无横向滚动、无覆盖、焦点可见、长标题可换行。
- 至少验证一个主任务路径，而不是只看静态截图。
- 不把旧 festival 截图的颜色或布局相似度作为验收指标。

## 7. 复杂度保留清单

以下内容当前有明确的生产职责，不因品牌重构删除：

- Work / ArchiveVersion 关系；
- manifest、SHA-256、core pack、blob 去重和白名单；
- 服务端 import job、preflight、单次 commit 和失败后按 draft 规则重试；
- EasyRPG 本地安装、缓存和存档隔离；
- 认证、角色、审计、GC 和危险操作保护。

以下内容当前不作为新增开发目标：

- 复杂推荐算法；
- 收藏、历史、评论等未存在的数据模型；
- 为了视觉统一而新增的泛型 UI 抽象。
