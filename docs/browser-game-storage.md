# 浏览器已安装游戏与自动清理

普通浏览器的 `/installed` 是本地游戏库，入口位于头像菜单「提醒」之后，在线游玩页另有管理链接。页面复用 `WorkCard`，按最后游玩的本地日期分组，提供本站占用估算、游戏文件合计和单个／批量清理。页面不要求登录，数据属于当前来源和浏览器配置，不随账号切换。

顶部复用项目 `PageHeader` 展示标题与数量，右侧提供批量管理及「存储」菜单。存储用量、闲置清理周期和清理全部操作集中在菜单内；周期可选 7 天、30 天、永不，默认 7 天，保存到当前浏览器的 `viprpg_web_play_preferences_v1`，页面与安装 Worker 共用。末尾缺少游玩日期的分组统一显示「更久以前」。

进入批量管理时，全选、已选数量、清理所选和完成均位于页头同一操作行；退出后恢复存储菜单。切换管理状态保持页头高度与列表位置。

## 存档管理

- 在本地游戏卡片点击存档计数，或在详情弹窗右栏进入存档管理，可查看槽位文件名、修改时间和大小，导入 LSD／ZIP、导出全部或所选存档，或选择具体槽位删除。
- 导入和导出复用游玩页组件，保留导入预览、逐槽位覆盖选择和存档锁。删除同样持有该作品及相关安装版本的存档传输锁，确认框列出选中槽位，只删除相应存档文件，保留配置、其他槽位及其他作品的数据。
- 安装索引升至版本 3，增加独立的作品名称索引，升级时从既有安装记录填充，之后与安装记录同事务更新。清理游戏资源不删除名称索引或存档；版本 1、2 的安装记录和文件索引原样保留，已有作品索引也保持原数据。
- 游戏库通过 IndexedDB 数据库名称发现游戏资源清理后保留的 IDBFS 存档；旧作品名称通过公开元信息补齐，离线或作品下架时沿用作品编号，仍可管理其存档。读取不存在的存档目录不会创建数据库。

## 截图管理

- 游戏库汇总截图的作品归属、数量与时间，包括安装资源已经清理的作品；读取作品列表时不创建图片预览 URL，打开详情时再加载预览。
- 详情图库按日期倒序分组平铺。开启管理时保持当前网格与高度，工具栏提供总全选，日期旁与图片左上方的复选框保持联动，支持所选截图 ZIP 下载和删除。图库工具栏与桌面右栏吸顶，两栏标题顶部对齐；批量操作与游玩页画廊共用逻辑。切换作品后释放旧预览 URL。
- 图片查看器挂载在详情弹窗标题下的区域，保留作品标题和关闭按钮。图片默认原尺寸展示，空间不足时缩小适配；支持左右按钮与方向键切换。底部缩略图横列使用透明背景、隐藏滚动条并跟随当前图片滚动；点击「←返回列表」或按 Escape 恢复图库，保留选择和滚动位置。
- 截图继续保存在原数据库，按作品归属，不复制到安装资源目录。删除某个作品的截图不影响其存档和其他作品的截图。本站 Android App 继续使用原生相册流程。

## 环境与存储

| 环境 | `storageKind` | 游戏资源 | 保留期限 |
| --- | --- | --- | --- |
| 本站 Android App | 原生安装记录 | 应用私有目录下 `games/<archiveVersionId>` | 不设置期限 |
| 支持 Storage Buckets 的浏览器 | `browser-bucket` | 每个安装版本独立的桶内 OPFS | 最后游玩后 7／30 天，或永不自动清理 |
| 不支持 Storage Buckets 的浏览器 | `browser-opfs` | 原 OPFS 目录 | 下次访问时执行同一周期设置 |

环境识别使用原生注入的 `window.VIPRPGAndroid`，不使用 Android UA。Android 手机上的普通浏览器按浏览器策略处理。主线程把选择的 `storageKind` 显式传给安装 Worker；读写和清理以安装记录中的存储位置为准。

Android App 不显示浏览器安装管理入口，不执行过期清理。主站调用原生安装队列，游戏和存档使用应用私有目录，截图使用系统相册 VIPRPG.org，详见 [Android 说明](../android/README.md)。不迁移首发前旧 APK 的 OPFS 数据。

桶名为 `viprpg-game-` 加安装键 SHA-256 的前 48 位，不超过 API 的 64 字符限制。桶只包含游戏 pack 和索引；安装记录留在原 IndexedDB，存档仍在 IDBFS `/work-saves/<workId>`，截图也不放进到期桶。

## 到期与续期

- 完成安装但未游玩：以 `readyAt` 起算；启动成功后使用 `lastPlayedAt`。
- 修改周期时同步更新已有游戏桶的到期值。Chrome 无法清空既有桶的到期值，「永不」使用最大有效 Date 时间戳 `8640000000000000` 作为原生到期上限，同时关闭应用层闲置到期判断；无需搬运或复制游戏文件。缺失的桶不会被重新创建。
- 会话持续运行时每分钟更新游玩时间，停止时再更新一次。页面恢复时核对资源是否仍存在。
- 打开作品、查看列表或读取桶本身不延长保留期。打开桶时总是传入记录计算出的截止时间，避免重置期限。
- 不再活动的未完成安装以 `updatedAt` 起算；没有留下任何资源的记录会移除。
- 网站进入、路由切换、恢复显示和前台定期检查时清理；安装前、读取安装列表时也会检查。
- 清理任务全局串行，每部作品另取排他 Web Lock。运行中的播放器持有共享锁，安装器持有排他锁，清理跳过两者。
- 浏览器回收不受应用的 Web Lock 控制；桶缺失时修正安装记录并要求重新下载，存档和截图保持原位置。

Storage Buckets 的 `expires` 不是准时释放磁盘的承诺。浏览器可自行回收，也可能等到下次访问才处理。普通 OPFS 的兜底只在网站执行时清理，不新增后台同步或推送任务。

存档仍可申请默认存储的持久化保护。游戏桶不申请持久化；持久化权限不改变用户选择的清理周期。「永不」停止本站按闲置周期清理，不阻止浏览器因存储压力回收数据或用户清除站点数据。

## 删除与状态

手动删除先取得游戏资源排他锁，再删除记录所指向的资源，最后删除安装索引及不再被引用的封面缓存。封面删除失败不会把成功的游戏删除误报为失败。批量删除串行处理，保留成功结果，并显示失败游戏与原因。

游戏库首先读取本地身份、安装记录、存档目录和截图索引，按最近游玩分组。旧数据只有存档或截图、缺少作品身份时，通过只读接口 `/api/works/local-library?ids=…` 分批补齐公开名称与封面，每批最多 100 项，并记入本地身份；离线或作品下架时沿用本地名称或作品编号，仍可管理资料。总占用来自 `navigator.storage.estimate()`，属于来源级估算；游戏文件合计来自各安装记录的 `installedBytes`。跨页状态通过 BroadcastChannel 和恢复显示时的读取更新。

点击游戏卡片打开详情弹窗，存档、截图计数直接定位对应管理区。图库使用直角缩略图，按日期分组，图片下方不附加拍摄时间。管理截图保持同一图库，通过日期与图片复选框执行批量操作。右栏提供初次游玩、启动次数与游戏文件占用；存档最多显示 3 个，超过时显示剩余数量，完整列表在存档管理中查看。存档导入、导出、按槽位删除沿用原有锁与确认流程。

`web_play_works` 保留作品名称、封面、最近安装键、最后游玩时间、初次游玩时间与启动次数；游戏资源清理后继续显示其游玩记录和资料入口，封面缓存随这些身份记录保留。初次游玩和启动次数在播放器初始化成功时记录，续期、切换页面和停止只更新最后游玩时间。新作品从首次启动完整累计；旧身份缺少首次时间时保持未知，启动次数仅累计功能启用后的启动，显示为 `≥ N 次`，尚未累计时显示 `—`。列表通过存档键读取名称和数量，通过截图索引键统计截图数量，打开详情时才创建图片 URL。只有用户进入存档管理时读取完整存档内容。

## 首发前已有缓存与后续升级

普通浏览器没有 `storageKind` 的旧安装在获得排他锁后一次性清理，随后按新机制重新安装，不保留旧浏览器存储模型。Android 环境完全跳过浏览器清理，原生目录由 App 独立管理。清理不触及存档和截图。

此规则仅处理首发前缺少该字段的旧缓存，不是上线后任意清除用户数据的授权。后续格式和 origin 变更须明确保护真实安装、存档与截图；必要的升级支持按实际客户端契约维护，不因“唯一当前模型”而直接移除。

## 验证边界

浏览器到期回收机制使用现有类型检查、变更文件 ESLint 和资源构建检查，尚不能据此声称实际到期回收已经验收。Android 原生闭环已另外进行模拟器验证，范围见 [验收记录](android-native-acceptance.md)。未新增自动化测试代码。

参考：[Storage Buckets 规范](https://wicg.github.io/storage-buckets/)、[Chrome Storage Buckets](https://developer.chrome.com/docs/web-platform/storage-buckets)。

## 本地数据兼容

浏览器安装数据库使用版本 3，从版本 1、2 增量升级，保留既有对象仓库；存档和截图仍使用各自的数据库。
