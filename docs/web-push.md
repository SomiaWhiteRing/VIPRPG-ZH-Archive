# 浏览器系统通知

系统通知位于个人中心的“隐私与偏好”页，在偏好内提供一个开关；开启后显示作品评论、回复、讨论版、赞、好友、私信、系统七类选项，样式沿用“在个人主页展示”的勾选组。开关控制当前浏览器，与其他偏好共用“保存设置”。

首次开启由用户操作触发浏览器通知授权。上方关闭作品评论提醒、好友提醒或私信时，对应系统通知选项取消勾选并禁用。授权及订阅准备完成后可以提交，隐私、偏好与系统通知设置在同一 D1 事务内保存。

订阅通过 endpoint 查询，关联当前账号和会话。关闭并保存后删除对应服务端订阅。`inbox_after_id/message_after_id` 记录接收起点：首次开启、重新开启、切换账号／会话或修改类别时从保存时的最新消息开始；类别保持原样时沿用起点。每个事件独立判断投递资格。

投递使用 Cloudflare Queues。提醒和已送达私信插入时，D1 触发器为存在相关订阅的事件在同一事务内产生待办。API 修改请求结束后读取待办，单次最多发送 99 个事件，并在需要时附加一个继续出队任务。Queue 接受任务后删除待办；失败保留，由后续 API 修改请求或既有每日维护重试入队。

个人[屏蔽设置](private-messages.md#屏蔽设置)同时控制站内提醒与系统推送。`0051_user_block_settings.sql` 使被抑制的互动不产生推送待办；已入队任务在投递前复核当前个人屏蔽与未读状态，私信继续按不可变的逐条投递状态过滤。系统、审批和举报等业务事项不受个人互动屏蔽影响。

队列携带事件类型、编号、订阅身份及分发分页位置，消费者按需读取内容与密钥。同一 Worker 同时作为生产者和消费者，每批 10 个任务，最多等待 5 秒，消费者并发为 1。分发任务每次检查最多 10 个候选订阅，按当前类别、权限和未读状态过滤后，为每个接收订阅创建独立投递任务；多余候选交给续页任务。普通提醒使用接收人索引，权限或维护者提醒分页核验。投递时以当前用户、会话、订阅、接收设置、权限、未读与来源可见性判断资格。

空待办通过一次有界查询结束处理。数据库写入集中在待办创建、入队后删除和失效订阅清理。事件有效期为 24 小时，发给推送服务的 TTL 使用剩余秒数。404／410 删除失效订阅；其他失败仅重试对应订阅的任务，最多重试 3 次。耗尽后结束该次系统推送，站内提醒或私信保留。Queue 和外部推送采用至少一次处理，显示端使用稳定通知 ID 合并重复。

## 内容与操作

投递端复用提醒详情的数据与可见性规则，生成发送者头像、标题和纯文本摘要，随加密推送传递。标题最多 100 字符、正文最多 240 字符；评论、动态和讨论显示对象名称及现有摘要，图片私信显示“［图片］”。头像沿用用户头像及默认头像，无发送人的系统通知使用站点图标。接收端直接展示推送内容，头像文件使用既有媒体入口。

可回复的评论、提及、动态、讨论和私信提供“回复”，定位现有编辑器并保留草稿，由用户编辑和发送。评论通过已授权的提醒找到准确主楼与回复目标；讨论沿用既有楼层、楼中楼与回复入口。新好友请求按当前状态提供“同意／忽略”，复用站内关系与忽略操作；接口核对当前登录账号及可操作性，失败时打开原提醒。审批、举报、获赞、申请结果、普通系统事件及汇总通过点击打开对应页面。

普通提醒和私信按实际查看自动标记已读，好友、审批事项通过既有业务操作处理。通知按钮的显示取决于平台支持，完整操作位于对应页面。

每条通知用账号、事件类型和事件 ID 作为显示标记，重复 ID 更新同一通知。站内提醒与私信各自最多显示五条，第六条到来后合并为该类汇总，包含数量和最近五个标题。汇总按该组 24 小时内的系统通知 ID 去重统计，点击分别打开提醒列表或私信列表。

点击聚焦已打开的目标页，否则新开页面。回复向已打开的对应页面传递聚焦指令，保留原编辑器草稿；好友操作成功通知已打开页面更新状态。通知 Service Worker 负责推送展示和点击处理。

## 配置与迁移

- `0050_web_push_subscriptions.sql` 增加订阅、类别、接收起点和待办触发器；固定开发种子同步该结构与迁移账本。
- 启用需要 `WEB_PUSH_ENABLED=true`、`WEB_PUSH_QUEUE` 绑定、`WEB_PUSH_PUBLIC_KEY`、`WEB_PUSH_PRIVATE_KEY` 和 `WEB_PUSH_SUBJECT`。页面读取公钥，服务端持有私钥。
- 开关在功能配置完整、浏览器支持通知 API 且处于安全上下文时显示；浏览器拒绝权限后开关禁用。该入口用于浏览器环境。
- 正式配置、迁移和部署遵循[正式操作确认边界](./production-deployment.md)。

## 候选资源与影响

正式候选队列名为 `viprpg-web-push-production`，由 `viprpg-zh-archive` 生产和消费；预生产独立使用 `viprpg-web-push-staging`。创建时建议消息保留 86400 秒。下列片段合并进各自环境的资源配置，预生产替换队列名；配置生成器保留 `queues`，启用时检查绑定、消费参数以及两环境隔离。

```json
{
  "queues": {
    "producers": [{ "binding": "WEB_PUSH_QUEUE", "queue": "viprpg-web-push-production" }],
    "consumers": [{
      "queue": "viprpg-web-push-production",
      "max_batch_size": 10,
      "max_batch_timeout": 5,
      "max_retries": 3,
      "max_concurrency": 1
    }]
  }
}
```

正式启用的确认批次包括：创建上述正式队列、更新 production 配置和 VAPID 密钥、应用 0050、发布包含生产者及消费者的候选代码。迁移后的新事件按订阅接收起点投递。小于 64 KB 的队列任务通常按写、读、删除共 3 次操作计；每个事件有分发任务，每个接收订阅另有投递任务，失败重试和续页另计。消费者另产生 Worker CPU 和 D1 读取，数据库写入来自待办维护和失效订阅清理。
