# 游戏领域架构

本文定义作品资料、作品关系、目录和归档版本的领域边界。D1 的当前字段、索引和 trigger 以 migrations 中的首发基线及有序增量迁移为准；本文不复制完整 SQL。

归档对象与文件完整性见[去重存储架构](./archive-storage.md)，认证和 ownership 规则见[认证与权限基线](./authentication-authorization.md)。

## 1. 核心模型

```text
Work
  作品身份与公开资料
  -> titles / creators / characters / tags / media / links
  -> work relations / translation relations / catalogs
  -> engagement stats / user play-favorite entries / comments
  -> ArchiveVersion 0..n

ArchiveVersion
  一份不可变文件快照
  -> manifest
  -> blob/core pack references
```

模型只有 Work 和 ArchiveVersion 两层。系列、发行层或翻译层不作为额外主实体；它们由 Work 之间的普通关系、翻译关系和目录表达。

### Work

Work 回答“这是什么作品”。它拥有：

- 原名、中文名、别名和简介；
- 用户自定义标题与正文的“更多信息”；
- 语言、原始发布日期、引擎、原创声明和翻译声明；
- 封面、浏览图和外部链接；
- 作者/制作人员、登场角色和标签；
- 普通作品关系、翻译关系、目录成员和共同上传者；
- `processing | published | hidden | deleted` 状态；`processing` 只表示服务器正在处理上传，不是用户保存的作品草稿。

`works.id` 是作品唯一身份。原名和中文名只用于展示与搜索，可以重复；公开路由使用永久不变的数值 ID。

作品内的作者、译者、登场角色和标签保留提交顺序，分别保存到 `work_staff.sort_order`、`work_characters.sort_order` 和 `work_tags.sort_order`。排序属于作品关系，不修改人物或标签本身；读取作品资料和列表时沿用该顺序。

所有保存入口使用同一日期解析器，接受真实有效的 `YYYY`、`YYYY-MM`、`YYYY-MM-DD`，精度由输入推导。上传者必须填写；管理员可以清空为 `null + unknown`，不能单独修改精度。

### ArchiveVersion

ArchiveVersion 回答“本站保存了哪份文件”。它直接归属于一个 Work，并记录：

- 来源；
- manifest SHA-256、文件策略、打包器和来源类型；
- 源文件、排除、纳入、blob、core pack、Web Play 和成本统计；
- 上传者、published/current、deleted/purged 生命周期。

发布后的 manifest 与对象引用不原地修改。文件发生变化时创建新的 ArchiveVersion，再显式切换 current。

## 2. 关系与资料对象

### 标题与上传者

- `work_titles` 保存可搜索别名；原名与中文名仍在 Work 稳定字段中。
- `work_uploaders` 表示可以对该 Work 执行 own-scope 维护的用户，不等同于 ArchiveVersion 的单次 `uploader_id`。创建作品时登记上传者；当前维护者可在编辑页添加维护者，或在提醒页通过维护申请，移除他人仍需 `work.maintainer.manage_any`。双方均须有 `work.update_own`，全站管理权限可代替操作者的本作维护资格；上传归档仍需相应上传能力。在“我的上传”及归档 own-scope 操作中与原上传者相同。申请及防滥用边界见[认证与权限基线](authentication-authorization.md#作品维护申请)。
- 创建新 Work 的上传者在 commit 中同时成为共同上传者；复用 Work 时必须经过 ownership 或 any-scope 授权。

### 普通作品关系

`work_relations` 表示 adaptation、prequel/sequel、same setting、alternative、character、collaboration、version/main version 和 collection/in collection 等关系。

- 关系不能指向自身。
- 有明确反向语义的关系由服务层创建一条系统反向记录；反向记录只能独立排序，不能脱离正向记录改语义。
- 同一逻辑关系只能存在一次；数据库索引与 `app/.server/db/relations.ts` 共同防止正反重复。
- collaboration 没有自动反向语义时按显式记录处理。
- `created_by_user_id` 记录创建者；公共入口保留添加，已有关系只允许管理员修改和删除。

关系类型与反向映射的唯一实现位于 `app/.server/db/relations.ts` 和 `lib/labels.ts`。

### 翻译关系

翻译关系把多个独立 Work 组织为原作与译本，不把译文压进同一 Work：

- 关联双方语言必须不同。
- 一个关系组最多有一个 original，其余成员是 translation。
- 同一 Work 在整个关系组中的角色必须一致。
- 双方仍保持独立资料、归档版本、上传者和公开状态。
- 创建、排序和删除通过 translation relation 服务执行，不能直接操作反向记录。

语言差异、唯一 original 和角色一致性同时由服务层和 D1 trigger 保护。

### 目录

作品页选择器与“我的目录”在 SQL 中先按 owner 和目录状态过滤，再搜索、计数和分页；选择器支持搜索与翻页，不从全站截取后筛选。

- Catalog 是用户拥有的有序 Work 集合，不是系列实体或系统分类法。
- `catalog_items` 保存默认值为 `0` 的非负整数排序值和可选备注，同一 Work 在一个目录中只能出现一次；目录先按排序值升序、再按 `work_id` 降序排列。
- own-scope 操作由 `owner_user_id` 决定；管理员 any-scope 仍经过目录服务。
- 公开页面只显示 published 目录中的可公开浏览作品（`public_works`）。

### 互动与评论

- `ViewStats` Durable Object 保存累计浏览与游玩数：两者均对所有访客统一按 UTC+8 自然日及指纹去重，登录状态及账号 ID 不参与公共计数去重。网页在线启动、ZIP 下载、外链下载页及 Android 安装完成共用作品游玩计数，Android 启动不计数。已有累计量及当日已计数的指纹保留，详见[统计说明](./view-statistics.md)。`user_work_entries` 保存登录用户最近游玩时间和收藏时间，匿名游玩不写个人历史；公共游玩计数不直接由个人记录条数计算。
- `user_work_tags` 以 `(work_id,user_id,name)` 保存收藏标签，外键绑定 `user_work_entries`；标签必须有有效收藏，取消收藏或删除收藏关系时自动清除，游玩历史不受影响。更新标签保留原收藏时间。`PATCH /api/works/:workId/me` 接收 `favorited` 和可选 `tags`，省略 `tags` 时保留原标签，空数组清空；收藏状态与标签在同一事务中保存。`GET` 仅返回登录用户本人的收藏标签和吐槽、该作品可公开展示的标签和本人常用标签。
- `user_work_entries.favorite_note` 保存最多 500 字的纯文本收藏吐槽，前后端按 Unicode 码点计数；数据库也限制长度及必须存在收藏。上述收藏 API 接收可选 `note`，省略时保留、空字符串清空；吐槽和标签在同一事务中保存，移除收藏时同时清空吐槽。吐槽随所属用户的收藏列表及作品的“收藏与吐槽”页展示，受收藏隐私设置保护，不进入游玩历史或全站标签统计。`0006_tags_favorites_and_read_indexes.sql` 为既有记录增加空吐槽并设置 500 字上限，不改变既有内容、时间和标签。
- `/games/:id/collections` 使用独立路由，导航仅含“概览 / 在线游玩（有归档时） / 收藏与吐槽”，侧栏与概览共用组件和数据加载。正文按收藏时间倒序、用户 ID 倒序稳定分页，每页 20 人，展示头像、昵称、时间和纯文本吐槽；未填写吐槽的收藏仍展示。仅公开活跃用户且开启 `profile_show_favorites` 的记录。侧栏收藏人数统计该作品全部活跃用户的有效收藏，包含私密收藏，人数链接到此页。上述查询均以作品 ID 限定，使用现有关系主键，不扫描全库重算。
- `comments` 必须且只能指向作品、作者、角色三者之一；公开查询要求目标为 published Work、公开作者或角色。评论使用主楼加同主楼平铺回复：回复回复仍绑定原主楼，`reply_to_comment_id` 只用于展示回复对象，不形成第三层层级。
- 主评论对外展示条目内楼号，不展示数据库 ID。楼号按创建时间、ID 正序计算，隐藏和删除的主评论仍占楼号；楼中楼不占主楼号。角色、作者条目的主评论按创建时间正序展示，游戏（含游玩页）按创建时间倒序展示，同一时刻以 ID 保持稳定顺序；游标方向与排序一致。
- 评论正文是纯文本和角色脸图表情；评论可编辑、软删除、隐藏和点赞。删除主楼会让整楼退出公开查询，作者自己的记录仍可见。
- 作品、作者、角色和游玩页的短评论楼中楼默认随主楼返回并按创建时间正序展示前 5 条；超过 5 条显示“查看全部 N 条回复”。展开后在楼内每页展示 10 条，支持上一页、下一页和收起；收起恢复前 5 条，不影响主楼分页。楼内分页数量包含删除占位；作品评论总数和公开个人页通过 `public_comments` 只计可读正文，要求目标、主楼、当前评论公开且两位作者均未被禁用（注销用户历史内容可见）；新增回复后自动展开并定位其实际所在页，加载失败保留当前内容并允许重试。
- 脸图表情采用不可变格子引用，个人库与默认清单分别管理；下架素材显示占位，取消收藏和角色解绑不影响历史引用。详见[表情库契约](./face-emoji-library.md)。评分及评分快照不属于当前模型。

### 作者、角色与标签

- Creator 表示作者或制作人员身份，保存唯一当前头像；`creator_aliases` 保存可搜索的历史署名和其他别名，`work_staff` 保存其在具体 Work 中的职责与本作署名。作者关联始终使用 Creator ID，作品页面显示本作署名，作者列表与作者详情展示头像。译者同样关联 Creator，以 `work_staff.role_key = "translator"` 保存本作署名并进入人物作品索引。默认制作职务为作者、策划、程序、剧本、美术、音乐和其他，仅收录直接参与本作创作的人；通用素材提供者不自动列入制作人员。
- 公开作者列表使用桌面两列、窄屏单列的轻量名片，展示头像、名称、别名、可选简介与去重后的公开参与作品数，不展示关联作品名称、封面或链接。未设置头像时沿用作者头像占位规则。作者首次署名公开作品后记录独立公开资格，之后即使公开作品数归零仍保留资料；列表只包含已取得公开资格的作者；名称与别名均可搜索，命中别名优先展示。默认按名称排序，也可按公开作品数降序排列，每页 30 位，总数使用相同公开与搜索条件独立统计。
- Character 表示角色身份，保存规范日语名和中文主名；`character_aliases` 保存可搜索的日语、中文别名及来源。
- `work_characters` 的每一行表示一次角色登场，保存该作品选用的中文展示名、头像、剧透级别、顺序和备注；同一 Character 可在一个 Work 中以不同形态重复登场，筛选仍使用 Character ID，不使用展示名反查身份。
- 公共 Tag 以名称为唯一标识，`tags.name` 是主键，`work_tags.tag_name` 引用名称，不保存标签 ID。名称沿用 NFKC、首尾空白清理和连续空白合并，唯一性沿用 SQLite `NOCASE`。管理端只维护命名空间与说明，不提供改名、合并或删除标签的功能。`work_tags.source` 仅保存关联的建立来源，不限制已有资料编辑权。作品资料编辑最多提交 10 个公共标签，前端选择器和服务端保存入口统一限制；提交完整标签集合时删除遗漏的作品关联，保留未变关系的来源，新增关系记录当前入口。
- 标签筛选链接使用 URL 编码后的名称（`/tags?tag=名称`），后台通过 `/admin/tags/edit?name=名称` 编辑；名称中的斜杠、井号和百分号均作为查询值处理。数字也是标签名称，不再解释成旧 ID，不保留旧 ID 或名称映射。用户端统称“标签”，仅具体标签作品页的来源筛选区分“公共标签 / 作品标签”；后者来自用户收藏标签。
- 用户标签直接保存名称，不加入公共 `tags` 字典；每次收藏编辑最多 10 项，每项最多 20 字，沿用名称规范化与 `NOCASE` 去重。收藏按钮打开已有 `TokenPicker`，在标签小标题下复用推荐行显示“常用标签”和“我的标签”，新建和编辑均保留已选推荐项并禁止重复添加。吐槽标题下不显示提示；剩余少于 50 字时在保存按钮左侧显示剩余数，超限变红并禁用保存。支持留空收藏、修改收藏标签和取消收藏。`0006_tags_favorites_and_read_indexes.sql` 为标签新写入和身份变更增加 10 项／20 字限制，保留迁移前已有数据。
- `public_user_work_tags` 汇总活跃用户给公开作品打上的标签，与 `profile_show_favorites` 无关；公开统计与推荐不暴露打标用户身份，个人收藏列表仍按隐私设置控制访问。已停用或注销用户以及非公开作品不进入统计、推荐和搜索。自己的常用标签与收藏筛选可读取本人私密收藏。详情页公共标签先按原顺序全部展示，不占用户标签的 20 项显示额度；用户标签排除同名公共标签后按本作品使用次数降序取前 20 项，同次数按名称排序。前者用 secondary 色，后者用 primary 色，不增加分组标题；每个标签旁的小数字为当前作品的用户打标次数加同名公共标签的 1 次贡献。读取只聚合当前作品的 `counted_user_tags`，与标签总览的全站累计次数区别开来。
- Creator 以 ID 区分身份，规范名和别名按规范化后的名称唯一，同一名称不能归属不同人物；输入已收录名称直接复用人物。Character original name、Character alias 和 Tag name 的唯一性及大小写规则以 migration 为准；不同角色可以共享中文译名。
- 上传表单提交已有角色 ID 和本作品展示名；修改已有角色的中文展示名时，未收录的名称在作品提交事务中添加为该 ID 的中文别名，不改动角色主名或身份。新建角色时同时提交日语名和中文名，由服务端在游戏提交事务中复用角色、新增别名或创建角色。

### 媒体与外链

- `media_assets` 按 Blob 内容唯一保存文件资料；`work_media_assets.role = cover | preview` 是作品图片用途的唯一来源。每部作品至多一张封面，创建和发布要求明确指定一张；同图可用于不同作品的不同角色。所有缩略图读取 cover，画廊将封面排第一并标注“封面”，其他图片标注“预览图”。作者头像直接引用单个 active blob。
- 合并保留目标封面，来源封面转为预览图；按内容去重，保留目标顺序并追加来源图片。缺少目标封面时拒绝合并。
- 媒体 Blob 必须 active。上传及指定作品／目录图片时只做轻量检查：识别实际文件头、读取尺寸并限制容量（作品／目录最多 20 MiB、最长边 32768、最多一亿像素），不解码像素、不计算图片块 CRC、不扫描压缩数据、不要求结束标记位于文件末尾。保留原素材的尾随数据和辅助色彩块，不据此拒绝图片；这不是文件完整性或可解码性保证。允许 PNG、JPEG、WebP、GIF，以及已有素材使用的未压缩 BMP；不接受直接 SVG、HTML 或无法识别的文件。论坛继续仅允许前四种且最多 2 MiB，头像继续限制 PNG、192×192、512 KiB。作品及通用 Blob 图片读取只用最多 64 字节文件头确定栅格图片 MIME，保留 `nosniff` 并流式返回原始字节，不信任历史 MIME，也不整张缓冲或重复解析元数据。
- 通用图片直链 `/api/media/blobs/{sha256}` 不查询 D1：先读已验证图片缓存，未命中再读取 R2 并识别实际图片格式。知道 SHA 即可读取仍存在的图片，包括未发布图片；作品隐藏、blob 状态变更或清理不撤回已有缓存。`blobs.public_at` 继续用于脸图库等发现筛选，公开资格不构成 GC 保留引用。隐藏作品编辑的 `/api/works/{workId}/media/{sha256}` 仍验证维护者／私有读取权限和图片所属作品，返回 `private, no-store`；它不承诺同一图片的通用 SHA 直链具有私有性。
- `work_external_links` 保存作品上下文中的官方、wiki、视频、下载页或其他链接；唯一 `download_page` 表达外部分发。ArchiveVersion 的 `source_url` 保存本次归档的发布地址。
- URL 校验集中在服务端安全 URL helper，不信任表单字符串。

## 3. 数据所有权

| 数据 | 所有者 | 修改方式 |
| --- | --- | --- |
| 作品身份和公开资料 | Work | Work 服务与管理/own-scope API |
| 别名、作者、角色、标签、媒体、外链 | Work | Work 更新事务同步维护 |
| 普通与翻译关系 | 独立关系记录 | 关系服务按创建者或 any-scope 管理 |
| 目录及成员顺序 | Catalog owner | 目录服务 |
| 浏览、游玩与收藏 | 当前用户及其目标 Work | 社区服务；公开查询检查作品状态 |
| 评论与点赞 | 当前用户及其目标 Work、Creator 或 Character | 社区服务；公开查询再次检查目标、主楼与评论用户状态 |
| 角色脸图表情 | 用户管理个人库、管理员管理默认清单 | 社区服务与 blob 生命周期 |
| 文件与来源 | ArchiveVersion | 归档服务；文件变化创建新版本 |
| 文件路径与 storage mapping | Manifest | commit 时冻结，不在 D1 逐文件编辑 |
| blob/core pack 生命周期 | 存储层 | 引用检查与 GC |

页面和 route 只做身份与 permission guard；上述服务必须再次校验 ownership、状态与引用完整性。

作品详情、指定 ID 集合、个人收藏/历史及作品关联读取按候选作品 ID 检查 `public_works`，避免先枚举全站公开作品。作者署名按 `(creator_id, work_id)` 反向索引计数；公开作品和作者评论分别以覆盖主楼及回复的目标索引定位，仍由 `public_comments` 检查目标、主楼和用户状态。角色分类浏览先构建父子及归属映射，再遍历分类树，避免每个节点重复过滤全部分类和归属。

## 4. 导入与更新

浏览器导入提交 Work 元数据、目标模式和 ArchiveVersion 元数据：

```text
target.mode=create
  -> 创建 Work
  -> 绑定当前上传者
  -> 创建 ArchiveVersion

external submission
  -> 创建并直接发布 Work
  -> 绑定当前上传者
  -> 写入封面、浏览图和唯一 `download_page` 外链

target.mode=update
  -> 验证目标 Work 与 ownership
  -> 按提交规则合并允许更新的资料
  -> 创建新的 ArchiveVersion
```

已有作品统一从 `/me/uploads/[workId]` 维护，并复用 `/upload` 的上传工作台。2k 系引擎支持本站归档或外部下载，新建默认显示“游戏文件”，编辑按实际来源回填。现有当前归档先作为已就绪信息展示，移除后才显示上传选择器；选择器的两个文件按钮旁提供“填写外链”，切换后只显示外部下载输入框。2k 系外链模式提供“返回游戏文件上传”，返回时清空外链输入；非 2k 系引擎始终使用外部下载。已有游戏文件或上传任务时须先移除或取消，才能改用外链或非 2k 引擎；非当前历史 ArchiveVersion 不参与切换判定。

没有选择新游戏文件时，保存只更新 Work 资料并保留当前 ArchiveVersion；选择新游戏文件时，同一次保存通过 `target.mode=update` 更新资料并创建新的 ArchiveVersion。转为外链时，同一 D1 批次取消当前归档并写入外部下载；转回本站归档时，archive commit 在同一批次删除旧外链并设置新当前版本。历史 ArchiveVersion 保留为不可变快照，但不会自动恢复为外链作品的当前版本。

来源方式是上传工作台的状态，不增加 Work 列，持久来源仍由当前 ArchiveVersion 与唯一 `download_page` 推导。恢复游戏文件草稿回到归档模式；仅有外链、没有历史归档的作品也可建立导入任务，归档提交仍校验所选引擎为 2k 系。详情页沿用现有按可用来源显示归档操作或“前往下载页”的分支。

Work 更新与 ArchiveVersion 创建必须在同一 commit 边界完成。不能先发布资料、后补文件引用，也不能因为同名作品自动合并；客户端必须提交明确 `workId`。

commit 的 schema 与校验由 `lib/archive/manifest.ts` 和 `app/.server/db/archive-commit.ts` 发布。前端字段不是领域契约的独立副本。

## 5. 生命周期

### Work

- `processing`：归档提交中的临时状态，不进入公开发现；超过 24 小时没有更新会由定时维护清理。
- `published`：作品资料进入公开列表，不因下载来源暂时缺失而退出。下载或游玩另要求目标 ArchiveVersion 已发布且为 current。
- `hidden`：保留资料但不公开；恢复来源不会将其自动发布。
- `deleted`：仅在管理后台可见和调整，不删除资料或归档文件。维护者经警告弹窗确认后可以删除作品，但删除后无法查看或恢复；只有管理员可恢复。

### ArchiveVersion

- 每个 Work 最多一个 `published + is_current` ArchiveVersion。
- current 必须 published 且未 purged，数据库 trigger 拒绝其他组合。
- 切换 current 由归档服务在同一事务中清除旧值并设置新值。
- 删除 current 后，服务层选择同一 Work 中合法的 published 替代版本；没有替代项时保持无 current。
- deleted 可以在 purge 前 restore；purged 版本不能恢复文件引用。

`public_works` 仅由作品 `status='published'` 决定资料公开性。失去最后一个下载来源后，作品资料、评论、关系和公开计数仍保留，前台显示暂无可用下载来源。创建与显式发布仍验证来源，已有缺源作品可维护资料；恢复来源后重新提供下载。当前下载与游玩入口要求作品 published、归档 published 且 current，不因资料可见而放开无效版本；历史归档协议的调整不属于本次公开性优化。

## 6. 查询边界

### 公开读取

- `/games`、详情、搜索、辅助索引、目录成员及计数、人物／角色作品、关联卡片、评论目标和媒体引用授权统一读取 `public_works`，过滤发生在分页之前。
- `/games/{id}` 只展示可公开浏览作品的公开关系和当前已发布归档。
- 作者索引读取独立的 `creators.public_at`；作者作品列表和计数仍限于 `public_works`。标签索引只显示有公开使用计数的条目；目录自身要求 published，目录成员要求 `public_works`。角色身份独立公开，没有公开作品也可搜索或打开详情；分类浏览按[角色分类](./character-index.md)中的归属规则展示。
- 普通关系的另一端如果不公开，不泄露标题、ID 或关系备注。
- 下载和在线游玩必须再次检查 Work 与 ArchiveVersion，而不是依赖详情页曾经可见。

### 管理读取

- private read permission 决定是否进入管理列表。
- 作品与归档 own-scope 按 `work_uploaders` 判断；已删除作品不向维护者开放。目录 own-scope 按 owner 判断。
- 删除、restore、current 和 any-scope 操作仍由领域服务检查目标状态。

查询实现集中在 `app/.server/db/game-library.ts`、`creator-library.ts`、`taxonomy-library.ts`、`relations.ts` 和 `catalogs.ts`。

## 7. 搜索

`/search` 由 [搜索页 loader](../app/search/page.tsx)按 `scope` 选择作品、讨论版、作者、角色、标签或目录，默认范围为作品。各范围独立查询和分页，不把其他实体混进作品结果。

作品关键词只匹配 Work 原名、中文名和可搜索别名，结果身份始终是 Work ID。作者、角色、标签和目录使用各自的公开查询；讨论版使用[论坛全文索引](./forum-discussion-design.md#8-搜索设计)。

作品库 `/games` 的筛选区只保留“浏览全部标签”入口，不展示标签列表或来源切换。`/tags` 浏览常用标签，`/search?scope=tags&q=关键词` 搜索标签名称；两页均不设侧栏或来源切换，将公共标签与收藏标签按名称合并，统一用 primary 色并按使用次数降序排列，不按来源优先排序。数字表示使用次数：所有符合公开统计条件的 `(作品,用户,标签)` 记录数，加上公共标签的关联作品数；同一作品上不同用户和公共来源的贡献分别累计，不因收藏列表隐私切换而变化。同名时优先使用公共标签的名称写法。旧 `/tags?q=关键词` 跳转到站内标签搜索。

`0006_tags_favorites_and_read_indexes.sql` 一次性初始化 `tag_usage_stats`，分别保存 `public_count` 与 `user_count`。`counted_public_tags`、`counted_user_tags` 保存已计入统计的关联，关联插入、移除与外键级联在同一事务内增减计数，归零后移除统计行。普通打标只处理当前关联；账号状态改变只同步该账号，作品状态变化只同步受影响的作品，引擎、当前归档和下载页变化不再影响公开计数，公开性仍以 `public_works` 为准。隐私设置不触发统计更新。标签总览、搜索、公共标签管理与推荐读取统计表，不再扫描全部打标关系；排序走统计表索引。个人常用标签仅查询本人的关联，作品详情仅查询该作品的已计数关联。作品资料与下载来源保持分离，新增下载规则不扩展公开计数同步入口。

`0006_tags_favorites_and_read_indexes.sql` 为外链公开性判断增加 `(work_id, link_type)` 索引，并为作品收藏列表增加按作品、收藏时间和用户 ID 排列的部分索引。收藏保存与作品收藏列表的公开性检查按绑定的作品 ID 查询，不构造全站公开作品集合；标签通过单条 SQL 批量写入，顺序未变时跳过更新。个人标签计数利用关联主键去重，按用户扫描已有覆盖索引。

选择标签后进入 `/tags?tag=名称`，默认显示两种来源合并后的作品结果，复用作品库的排序和分页，不显示“当前筛选”行。仅此标签作品页设右侧边栏，提供“全部 / 公共标签 / 作品标签”来源筛选和返回入口，不再单设标签搜索框，复用作品库侧栏的分区与选项样式。来源参数为 `tag_source=all|public|user`，默认 `all`；切换来源保留当前标签和排序并重置分页。旧 `/games?tag=名称` 链接保留查询参数跳转到 `/tags`。`0006_tags_favorites_and_read_indexes.sql` 将统计排序索引调整为使用次数与名称，与总览和搜索的排序一致。

用户标签链接为 `/tags?tag=名称&tag_source=user`，结果列表和分页按去重作品数计算，同一作品被多位用户打上同名标签只返回一次；列表顶部的作品总数与标签的使用次数是不同指标。`/me/favorites?tag=名称` 和公开个人收藏页按收藏所属用户的标签筛选，并沿用个人收藏的可见性控制。两个收藏页共用专用的“收藏标签”侧栏，以纵向列表展示标签及该用户收藏中的使用次数；选中标签只高亮对应行并回到第 1 页，“全部”恢复完整收藏，不显示横排标签或“当前筛选”行。收藏时间旁展示该用户给作品打上的标签，点击仍在这位用户的收藏内筛选，吐槽显示在其下方。我的收藏提供与目录条目一致的“编辑／移除”操作；他人的收藏提供“加入收藏”，状态以当前查看者自己的收藏为准，弹窗也仅编辑查看者的标签和吐槽。

小规模数据直接查询规范化表。只有真实数据量证明查询不可接受时，才引入由这些表生成的物化搜索索引；不得让搜索索引成为可独立编辑的第二份资料。

## 8. 扩展资料

采用三层模型：

1. 经常查询、筛选或校验的字段进入明确列。
2. 多值、可关联或需要完整性的资料进入规范化关系表。
3. 低频、只展示、不参与权限和查询的资料可以进入经过 JSON schema 约束的 `extra_json`。

“更多信息”使用 `works.extra_json.moreInfo` 保存有序的 `{ title: string, body: string }[]`，结构与长度由 `lib/work-more-info.ts` 统一校验；未填写时为空列表。它属于可编辑的 Work 资料，不属于 ArchiveVersion 或不可变 manifest，也不进入搜索索引。

所有资料保存入口以完整列表替换 `moreInfo`，空列表表示清空；其他 `extra_json` 键保持原值。条目没有独立身份、关联或修订历史，权限沿用作品资料维护权限。

没有管理员动态建字段的真实需求前，不引入 EAV、自定义字段系统或通用 entity/attribute 抽象。

## 9. 身份纠错与合并

合并仅在后台执行。人物合并保留目标资料，转移别名、署名和评论；作品合并保留目标资料与下载入口，转移归档、维护者、评论、收藏、目录成员及关联，将来源作品设为 deleted。同文件归档保留目标归档 ID；冲突的署名、目录备注或翻译关系拒绝合并，事务全部撤销。不同语言或引擎的作品不合并。浏览器存档仍按原 Work ID 保存，不随后台合并自动转移。

本站只收录有下载来源的作品，不引入仅资料条目。人物名称唯一，本作署名单独保存；作者表单完整保留多位作者。

同文件归档仅在发布状态和清理阶段一致时自动去重，否则报告冲突的归档 ID，要求管理员先统一状态。最终事务再次限制删除条件，状态变化时整次合并回滚，不自动恢复归档或切换当前版本。合并游玩记录时，两边均未游玩仍保留 NULL；只有一边有时间则保留该值，两边都有时间则取较晚值，不把收藏计为游玩。用户标签在收藏合并后转移到目标作品，同一用户的同名标签去重，保留目标已有标签及来源非重复标签。收藏吐槽保留非空或相同内容；同一用户有两条不同的非空吐槽时拒绝合并，并在事务内再次校验，防止静默丢失吐槽。合并后的收藏标签也必须满足 10 项／20 字限制，超限时拒绝合并，不截断或丢弃标签。

作品合并要求来源和目标的翻译声明、原创声明分别一致。冲突时提示先统一声明；最终事务在转移任何关联前再次检查，冲突则整批回滚，不自动修改目标声明。

## 10. 不变量

- Work ID 是作品唯一身份；标题不是唯一键。
- ArchiveVersion 直接属于 Work，不存在中间 Series 或 Release 层。
- 文件路径只属于 manifest；D1 只保存对象引用和统计。
- 同一 Work 最多一个合法 current ArchiveVersion。
- 普通关系不能自关联或逻辑重复。
- 翻译关系语言不同、最多一个 original，且成员角色一致。
- Catalog ownership、关系创建者和 Work uploader 是不同的 own-scope 来源。
- public 查询必须从完整 published 链开始，不能先读私有对象再在 UI 隐藏。
- 废弃领域模型直接从 migration、代码、文档和 seed 中删除，不保留兼容层。

## 11. 验证

测试分层遵循根目录 `AGENTS.md`。敏捷阶段按改动选择最小验收：

- 类型、静态架构或权限规则变化运行 `npm run check`
- 数据约束或稳定领域契约变化运行 `npm test`
- 模型调整时用 `rg` 扫描废弃表、字段、路由和类型残留，结果仅作为当次变更证据
- 对照 migrations 中的完整迁移链检查本文不变量，而不是复制 SQL

预生产或发布前统一运行 `npm run verify:preprod`；流程测试和生产构建不作为每次领域编辑的固定门槛。

涉及已有数据或外部 API 契约时必须单独设计迁移；当前无生产数据时直接推进唯一当前模型。

### 独立公开资格与请求内复用

`0010_independent_publication.sql` 为 blob 和作者增加 `public_at`，仅回填迁移时可确认的公开引用，未来由发布、署名、图片绑定和素材批准的事务登记。公开标记不构成 GC 保留引用；孤立文件仍遵循原回收规则。角色脸图要求字节已公开、存储活跃且素材未被拒绝，不再追查来源作品。评论/论坛图片继续按内容审核权限读取并返回 `no-store`。

作品及作者详情读取可以在同一 `AppRuntime` 中记录目标已公开，评论初读复用此信息，评论 SQL 仍执行自身公开过滤；独立 API 请求没有此标记，仍检查目标。标记不跨请求缓存，也不用于写入授权。安装元数据与安装总量共用一次版本查询。
