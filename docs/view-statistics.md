# 作品与主题浏览量、作品游玩统计

作品详情和在线游玩共享作品 ID；主题的所有分页共享主题 ID。页面实际可见时才上报浏览量。作品游玩数包含网页在线启动成功、点击下载 ZIP、点击外部下载页，以及 Android 安装完成；匿名和登录用户均计入，各入口共用同一作品计数。评论数及收藏仍沿用原业务模型。

时间线的「首次游玩」使用独立的 `/api/works/<workId>/first-play`，只由网站与 Android APK 共用的播放器在引擎 `ready` 后调用，不复用本页的下载／安装上报入口。服务端按登录账号与作品永久去重，关闭时间线时仍消耗首次资格，但不产生动态；重新开启不补发。请求采用当前同源会话，不阻塞游玩；断网、失效会话和请求失败不创建延期队列，因此未成功送达的离线启动不保证进入服务器记录，也不把重连时间写作先前启动时间。

## 计数口径

- 浏览与游玩均按 UTC+8 自然日去重：`日期 + 条目类型 + 条目 ID + 当日访客摘要`。作品浏览（`work`）、主题浏览（`topic`）和作品游玩（`play`）分别计数。
- 所有访客均按指纹识别，同一作品、同一指纹当天只计一次；UTC+8 零点后发生的新操作可以再次累计，不必距离上次计数满 24 小时。登录状态和账号 ID 不参与公共计数去重，同一指纹当天切换账号、登录或退出也不会重复计数。
- 访客指纹为随机日盐作密钥的 HMAC-SHA256，输入是站点、Cloudflare 提供的 IP、User-Agent。只使用当天的盐生成当日摘要，次日使用新盐。不保存原始 IP/UA，不设置身份 cookie 或 localStorage。相同出口与浏览器可能合并，换网络或浏览器可能重复；登录用户也遵循相同规则。
- 浏览器内存中的每日集合只减少重复浏览请求；公共游玩由 DO 最终去重。只在发生新操作时上报，不轮询，不因停留跨日自动增加一次。
- 网页在线游玩在引擎 `ready` 后上报，访问游玩页、安装网页本地资源或启动失败不计入。详情页和列表的 ZIP 下载、外链下载页在点击时上报，不等待下载完成，也无法确认站外游戏实际启动；普通官网、介绍等外部链接不计入。
- Android 在 ZIP、索引和安装完成记录校验、持久保存后，由原生安装任务上报；排队、暂停、安装失败及启动本地游戏不计入。原生请求使用 WebView User-Agent 参与相同指纹去重，同源会话 Cookie 用于更新登录用户的个人游玩历史；不依赖页面保持打开。统计失败只记日志，不将已完成安装改成失败，也不在启动游戏时补报。
- 有效登录用户的每次上报仍更新本站最近游玩时间，即使公共计数已经去重；匿名请求不写个人记录。Android 启动只更新设备本地最近游玩时间。统计失败仍更新有效登录用户的历史，统计接口返回相应错误，下载、跳转与游戏启动不受影响。
- 两类上报入口均检查同源、正整数 ID、明显机器人 UA 和 IP 限流。浏览上报不查询条目是否公开或存在；游玩上报保留作品公开性检查。访问权限仍由原页面和业务 API 检查；成功上报不代表游戏确实运行，伪造请求仍可能产生计数，本方案不是反作弊系统。

## 存储与读取

每个 Worker 环境绑定一个 SQLite Durable Object 类 `ViewStats`，使用固定对象名 `site`。浏览和游玩共用该对象、日盐及清理机制，通过 `kind` 隔离计数，不新增 binding 或 D1 schema。生产、staging 和本地状态各自隔离。总数长期保存在 `totals`；`play_visitors` 按 `(day,id,visitor)` 保存游玩去重记录，新记录的 `expires_at` 为次日 UTC+8 零点，仅用于清理，不参与去重判定。浏览摘要按当天及前一天的保留窗口清理，游玩摘要过期后清理；仍被摘要引用的日盐不会提前删除。分批清理或平台故障可能延后实际删除，但不影响次日计数。日盐先安排过期 alarm 再入库；两类摘要各批最多清理 5,000 条，必要时继续下一批，清空后不再唤醒。没有按条目扫描、五分钟任务或计数回写 D1。

已有累计数原样保留，不追溯重算旧口径。尚无总数的作品仍将 `user_work_entries` 中该作品的现有游玩账号数作为一次性初始值，不再导入账号 ID。初始化和新增计数在 DO 中串行、事务处理，后续个人历史更新不再加到公共计数。旧指纹记录中当天已计数的访客继续去重，前一天的记录不再阻止当天计数，原 `expires_at` 保留到正常清理。此前只按账号计数的操作无法还原访客指纹，这些访客从新口径首次有效上报建立当日记录并增加计数。已部署 DO 中的旧账号去重表不再读写，本次切换不清理其中的数据。

展示时仅缓存公共计数。边缘 Cache API 中 15 分钟内的计数直接复用，缺失或过期的 ID 每批最多 128 个通过一次 DO RPC 读取。首页、游戏列表、详情和游玩页使用同一游玩计数；“最多游玩”排序和“最多浏览”一样，由 DO 按完整筛选 ID 集排序后返回当前页。读取由真实页面请求触发，不主动刷新；Cloudflare 各机房缓存独立，可能提前淘汰，15 分钟不代表全球只请求一次。缓存保留期为 24 小时，DO 故障时优先显示已有旧值；没有旧值时浏览显示 `0`，游玩显示 D1 提供的账号初始值，该兜底值不写入 DO 或缓存，故障写入 Worker 错误日志。

同一请求按类型和 ID 复用计数读取，包括尚未完成的批量读取。Worker 实例内另存最多 4096 个已取得的公共数字，以 DO binding、站点、类型和 ID 隔离，按最近使用淘汰；沿用数字原始时间与 15 分钟新鲜期，命中不会延长过期时间。实例间只通过既有边缘缓存和 DO 共享数据，活动 I/O Promise 和认证页面数据不跨请求保存，故障回退值不进入实例缓存。作品详情正文和侧栏还在同一请求复用公开评论、收藏等统计，个人收藏状态单独查询。

同一指纹当天重复上报同一作品的游玩或同一内容的浏览，在 DO 中不会增加对应总数，也不会写入新的去重记录；它们仍消耗 Worker/DO 请求以及去重查询。新计数写去重表和总数表，过期删除也计入 DO SQLite 写用量。前端浏览去重、批量读取和缓存负责减少这些开销。额度由整个 Cloudflare 账号共享，不能只凭单站访问量承诺不超套餐；IP 限流也不是总费用硬上限。

## 作品合并

作品合并时同时累加浏览与游玩总数。先在 DO 初始化两个作品的游玩初始值，再执行 D1 的合并事务，避免个人历史搬迁／去重后丢失尚未导入的旧计数；初始化失败则不执行合并。D1 事务写入原有 `view_stat_merges` 待办；随后通知 DO 原子转移两类总数及每日去重记录，同一天的相同指纹合并为一条，游玩记录保留较晚的清理时间。DO 保存操作 ID，重复投递不会再次累加。转移完成后删除待办；失败由原有每日维护任务按 ID 顺序重试，每次最多 50 条。正常浏览上报和 DO／缓存计数读取均不访问 D1；游玩初始值来自页面已有的 D1 查询，游玩上报另行验证公开作品并读取初始值，登录用户同时更新个人历史。维护任务只读取这张小待办表，不扫描作品或主题。

历史累计总数沿用相加语义，无法对已清理的历史访客做跨作品重新去重。合并不会建立永久 ID 别名；源作品以后恢复或再次收到上报，将从新的计数开始。缓存中的合并前计数在下次过期读取时更新。

## 配置与当前 schema

`wrangler.example.jsonc` 声明 `VIEW_STATS` binding 和 SQLite `exports.ViewStats`。当前 Wrangler 支持声明式 exports，不再叠加 DO migrations 配置。生产和 staging 均需单独声明 binding，不设置跨 Worker 的 `script_name`。

`VIEW_RATE_LIMITER` 使用独立的、账号内唯一的数字 `namespace_id`，每个 IP 在每个 Cloudflare 机房每分钟最多 120 次上报；不能与认证邮件限流共用 namespace。部署 secrets 中的 `WRANGLER_CONFIG_JSONC` 也必须包含此绑定，配置生成脚本会检查。仓库固定限流策略，私有配置提供 namespace ID。部署前按[环境配置来源](./staging-deployment.md#环境地址与配置来源)核对账号中的实际 ID。

首发使用 `0001_init_archive_schema.sql` 基线及后续有序迁移，正式初始化后不改写已应用文件；现行模型不保留废弃 D1 计数表或双写。固定开发种子不包含 DO 计数。`db:local:reset` 一并清理本地 D1 和 DO，避免重用内容 ID 时串入旧计数；该开发规则不能用于清除正式累计量。正式 DO 身份、计数、备份／恢复与迁移须单独列入批准范围，D1 备份不涵盖 DO；见[正式手册](./production-deployment.md)。
