# 提醒产品与界面契约

提醒提供讨论互动、角色申请、角色变更和系统消息的站内入口。讨论内容规则见[讨论设计](./forum-discussion-design.md)，角色审批规则见[认证与权限基线](./authentication-authorization.md)。

## 接收范围

| 事件 | 接收人 | 导航目标 |
| --- | --- | --- |
| 主题新增普通楼层 | 主题作者 | 新楼层 |
| 无定向楼中楼回复 | 父帖作者 | 新楼中楼 |
| 定向回复楼中楼 | 被回复楼中楼的作者 | 新楼中楼 |
| 首帖或普通楼层收到点赞 | 被赞帖作者 | 被赞楼层 |

仅向活跃账户生成互动提醒。每次回复只通知直接接收人，不额外抄送主题或父楼作者；自己回复或点赞自己的内容不提醒。参与讨论不等于订阅。

作品详情短评论、楼中楼点赞、@、订阅、私信、外部推送、提醒偏好、互动聚合和历史互动补发不属于本功能。

## 持久事件与内容边界

- 回复和提醒在同一 D1 批次中提交，沿用论坛发布的请求幂等与写入门控。失败、重试、编辑与恢复内容都不会重复生成提醒。
- 点赞关系实际新建时才尝试写入提醒。同一操作者、目标帖与接收人只有一个点赞事件；取消点赞不删除历史提醒，再次点赞不新增、不重置已读、不改变原时间。
- 点赞提醒说明曾发生的互动，不表示当前点赞关系或实时点赞总数。
- 复用 `inbox_items` 和 `inbox_item_reads`，互动类型仅支持定向个人收件；角色申请仍按已有个人或权限收件规则读取。事件唯一键和论坛引用由 migration 约束，不在自由文本中保存可执行跳转地址。
- 列表、未读数、单条读取及全部已读采用相同收件可见性。申请列表和待办计数采用相同当前审批能力判定；可查看申请不等于可以处理。
- 标题和摘要从当前可公开内容生成，纯文本显示，不保存正文快照用于绕过公开性检查。目标、必要上下文或账户不可公开时，显示“相关内容已不可用”，不输出相关原正文、标题、身份或用户链接。
- 已注销账户在仍可公开的内容中显示本站统一名称与默认头像，不提供主页链接。恢复内容公开性不会制造新事件或新的未读。
- 不可用提醒仍可单独或批量标记已读，未读计数不会静默排除它。

写入入口为 [publishForum / likeForum](../app/.server/forum/mutations.ts)，提醒语句集中在 [notifications.ts](../app/.server/forum/notifications.ts)；查询与阅读操作集中在 [inbox.ts](../app/.server/db/inbox.ts)。

## 页面与列表

`/inbox` 的分类、只看未读和页码通过 URL 保存。全部按时间倒序，同时间按 ID 倒序；每页 30 条，使用站点数字分页，越界页码回到有效页。

| 分类 | 内容 |
| --- | --- |
| 全部 | 当前用户可见的全部提醒 |
| 回复 | 普通楼层和楼中楼回复 |
| 赞 | 点赞事件 |
| 系统 | 角色申请、角色变更、系统通知 |
| 待处理 | 当前用户仍可批准或驳回的 pending 申请；仅有审批能力者可见 |

“只看未读”可与分类组合。页头数字表示全部未读，待处理入口数字表示待办数；普通分类不堆叠计数。申请人可在系统分类查看自己的申请与结果。

使用紧凑 `PageHeader` 和单份响应式列表，沿用站点浅米背景、青绿色主色、字体、按钮、头像和分页组件。行间分隔线替代独立带阴影卡片，不重复输出桌面表格和移动卡片，也不显示角色说明或统计卡。

每条互动以操作者、事件、主题标题、楼层位置和时间为主要信息，回复可有两行摘要。用户主页与内容目标分别为独立链接。未读通过圆点、字重和可访问状态共同表达。申请状态只在角色申请上展示，不给所有消息套审批状态。

桌面端时间和操作靠右，移动端放到内容下方；以 390px 宽度和左右 16px 页面留白为基准。分类可横向滚动，页面本身不得横向溢出。长中文标题、长用户名和 200% 缩放允许换行，操作保留键盘焦点与触摸范围。

分类与分页加载期间保留已有结果。空状态区分全部为空、没有回复、没有赞、没有未读和没有待办；失败显示“提醒加载失败。”及重试，不伪装为空列表。标记和审批的操作结果使用[全局 toast](./ui-feedback.md)，失败后原按钮仍可重试，成功后焦点回到稳定筛选工具栏。

## 阅读、定位与申请处理

- 无需当前用户批准或驳回的提醒，在列表或提醒详情的可见区域连续停留 1 秒后，通过 POST 自动标记已读；页面在后台、预取或仅加载到屏幕外的条目不计为看过。需要当前用户处理的申请保留手动已读及审批操作。
- 自动已读同步行状态、页头未读数和全站入口；不重排当前列表，“只看未读”中的已读条目在下次筛选、翻页或刷新时移除，避免阅读中跳动。自动标记失败保留未读与手动标记入口。
- 内容链接经过 `/inbox/[itemId]` 验证收件人与当前公开性，用 `forumLocation` 计算当前页码及锚点，再进入主题页。失效目标提供不可用提示与标记已读入口。
- 主题页保留提醒 ID，在目标内容实际展示且页面可见后，通过 POST 标记该条已读；支持新标签页打开。服务端再次校验收件人及主题、楼层、楼中楼关联。GET 和路由预取不写已读。
- 标记失败不拦截阅读，提供重试与返回提醒入口。
- “全部标记已读”跨分类、跨分页，作用于服务端写语句开始时的全部可见未读记录；集合式写入不设条数截断，之后到达的新事件保持未读。
- 阅读状态与申请业务状态独立。已读申请仍可待处理；批准或驳回后，在原有审批事务中标记当前操作者已读，不改变其他管理员的个人阅读状态。
- 批准／驳回继续受现有权限、账户与角色层级、本人限制及角色状态约束。并发已处理时显示最新结果，不声称重复操作成功。

## 全站入口与更新

提醒入口保持在页头用户菜单内，桌面和移动端均显示“提醒”及未读数，不在菜单外单独放置铃铛。有未读时，页头头像右上角显示红点，用户菜单的可访问名称包含未读数；全部已读后红点消失。使用现有未读格式及“提醒，N 条未读”的可访问名称。未读更新组件保持挂载，不依赖菜单是否展开。

页面首次进入使用服务端初值；站内导航、窗口重新聚焦、页面恢复可见时查询未读数量。短时间重复触发合并，禁止重叠请求；标记已读或处理申请后立即同步。请求失败保留上次成功值，下次事件触发时重试。

不做定时轮询或周期性页面刷新。用户持续停留同一页且没有上述事件时，不主动更新新提醒；浏览器关闭后不推送。普通计数更新不重排当前提醒列表，不干扰帖子草稿。

入口组件为 [InboxIndicator](../app/components/inbox-indicator.tsx)，查询端点为 [GET /api/inbox/unread](../app/.server/endpoints/api/inbox/unread/route.ts)，由 [Hono API](../app/.server/api.ts) 注册，仅返回当前登录用户未读数并禁止响应缓存。

测试授权和验收分层遵循根目录 [AGENTS.md](../AGENTS.md)，操作入口见[维护与回归手册](./maintenance-regression.md)。
